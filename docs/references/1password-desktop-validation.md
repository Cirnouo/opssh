# 1Password Desktop SDK validation procedure

This procedure requires explicit approval for the exact disposable item, the intended test actions, and use of the local desktop application. The normal build, test and CI pipeline uses the offline fixture.

1. Prepare a dedicated SSH Key item in a 1Password test vault and record its expected public fingerprint. Obtain approval for listing vault and SSH Key item metadata on the test account. Record Windows architecture, 1Password desktop version, and SDK version. Keep actual account and item identifiers out of public evidence.
2. Verify the signed-in test account in the local 1Password application and enable CLI and SDK integration with operator approval. Install the official 1Password CLI and launch the production Release tray with a fresh test configuration. Use a dedicated vault that contains only the approved test key.
3. Open the 1Password picker and select the approved test account. Inspect the official 1Password prompt and verify the requesting core process and account scope before approving. Confirm that the vaults are listed and the public index is empty. Allow only the dedicated test vault, then choose Discover SSH Keys. Check that the public-only reference resolves the expected canonical key and fingerprint. Test ssh-add -L against the process-local pipe. If the public field selector fails, record the failure and stop before requesting the private field.
4. With explicit approval for private reads of the dedicated test key, enable DEBUG diagnostics and select **Preload private key**. Check the per-key result and the start and completion records. Retain only the outcome, timings and safe diagnostic category. If preload fails, resolve the test failure before continuing. With the public key in a temporary public file, use system `ssh-keygen -Y sign` on a generated local message and verify with `ssh-keygen -Y verify`. Verify the application, PID and key fingerprint in the opssh Windows notification, then select **Allow once**. This performs local signing without an SSH connection. Compare the derived identity to the index and retain only the public fingerprint, algorithm, timings and outcome.
5. Repeat with a denied or canceled prompt, a changed test public key and a late provider response if reproducible. Confirm that clearing the private key preserves the approval, and revocation preserves the loaded key. Exclude the test vault and verify that its keys and approvals are withdrawn. Re-include the vault, discover keys manually and verify that a subsequent request needs a new approval. Observe that locking 1Password revokes its read grant, while already loaded material follows the selected opssh cache policy.
6. Exit through the tray and restore the test shell's prior agent selection. Close the test configuration, retain only sanitized evidence and identify any unexercised conditions.

The production adapter uses the public `WithDesktopAppIntegration`, `Vaults.List` and `Items.List` interfaces for authorization and discovery metadata. Public discovery uses `Secrets.ResolveAll` for batches and `Secrets.Resolve` for individual public refreshes. A private read calls `Secrets.ResolveAll` with one reference using the documented `private key?ssh-format=openssh` selector so the adapter can distinguish structured field errors. Step 3 verifies the public field independently.

Sources: [SDK setup](https://www.1password.dev/sdks), [secret reference formats](https://www.1password.dev/sdks/concepts#ssh-format), [Go desktop implementation v0.4.1](https://github.com/1Password/onepassword-sdk-go/blob/f60aea196b471a9c35ddad5f9096e5fd2b5c939c/internal/shared_lib_core_windows.go).
