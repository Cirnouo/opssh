# Windows agent behavior

The initial Windows x64 implementation consists of the Go agent and the resident C# WinUI 3 tray. The tray starts its exact bundled child and creates a dedicated duplex channel. It hands over only the connected client endpoint and its real process handle. The core verifies the endpoint PIDs against the handle, sends its greeting, and serves the SSH pipe. The control protocol uses length-prefixed UTF-8 JSON v1. Private key material and SSH signing inputs do not cross the tray channel.

The SSH transport is a per-logon byte pipe. It rejects remote clients, reserves the first instance and keeps a fixed pool of 16 overlapped instances. The DACL restricts client access to the logon SID and excludes additional server instance creation. Requests use kernel pipe identity, the last-read logon token, and retained process handles with creation times. The parent chain includes only verified live same-logon instances, with strictly earlier creation times. Missing or unsafe links end traversal. An unidentifiable requester cannot sign. A cached grant matches the exact key and process instance. Windows recorded parentage and connecting-PID identity do not establish an isolation boundary against same-logon code with access to other processes or duplicated handles.

List and Sign follow RFC 9987. The core exposes configured public blobs, Ed25519, and RSA 2048 to 4096 with the SHA-256 or SHA-512 request flag. It returns failure for unsupported operations, including forwarded session-binding, identity mutation and RSA SHA-1. A raw agent signing request provides no verified remote destination. Frame lengths, pending requests and connection concurrency are bounded. The SSH client selects the opt-in pipe in its own environment. See the [user guide](../user-guide/README.md#select-agent) for selection and rollback.

The tray initiates initial account connection. The user supplies the name or ID of an account already signed in to 1Password Desktop with SDK integration enabled. The 1Password window handles its own verification and authorizes the Go core. The core lists accessible vaults and active SSH Key item overviews, applies the configured scope and resolves only public fields for indexing. At startup the core loads the saved account and public index. List serves that index, and status polling uses local state. An approved signature that needs private material requests it on demand. A restarted core needs a fresh SDK grant when it first requests data from 1Password. Index refresh remains a user action.

The public configuration is stored under `%LOCALAPPDATA%\opssh`. It contains the connected account, scope rules, cache policies and the public index with stable item references, names and canonical public bytes. The account default is include for new configurations. Vault rules override the account default and item rules override the containing vault. Migration preserves the old manually selected scope. Applying an exclusion retires the affected identities, grants and private material before fetching any public fields. Refresh withdraws the old catalog before publishing current, unambiguous identities. The scope governs which public keys the app advertises and which items it reads for signing. The SDK's authorization is account-wide.

The index holds up to 64 scoped keys. Discovery scans up to 256 vault overviews and 8,192 item overviews per scoped vault. An over-limit index stays empty and the tray explains the limit. The scope editor shows up to 64 vaults and 128 SSH items. New overrides use visible entries. Saved overrides can be removed individually even when their entries are outside the visible list.

Private lookup is delayed until a sign is authorized, or a user explicitly requests preload. Loaded material is checked against the exact requested public key. A signer owns its temporary private material independently of the public catalog.

| State | Owner and lifetime |
| --- | --- |
| Desktop SDK permission | 1Password manages account/process access. The UI shows observed request state, including recent success, failure and timeout. |
| Loaded private material | The core caches it in memory, fixed 5 minutes by default. Fixed time starts at import; idle time is renewed after successful signing. |
| Use approval | The core keeps it in memory, fixed 10 minutes by default. Fixed time starts at approval; idle time renews after successful signing. Only a successfully published signature installs a reusable grant. |

Each cache supports off, fixed, idle, until-lock and until-exit modes. Host approval includes the host itself and subsequent verified descendants. The exact host must remain alive. Direct mode covers the requesting instance. Once applies to one pending request. The core checks connection, process, key generation and approval before loading and again before signing and publishing. A late result cannot restore invalidated state. Eviction clears only key material. Revocation clears only approvals. Lock clears both and keeps the public index available. Closing or losing the control channel shuts down the core. Reconnection starts a new core and an empty approval state. Account switching restarts the core and resets the selected index.

The dashboard control commands separate vault selection from public key discovery. Vault inclusion changes scope, and exclusion retires affected identities immediately. Dashboard discovery withdraws the persisted index during the scan and retains eligible transient state only for matching public identities after a complete result. The candidate core can authorize a selected account and read vault metadata before the tray transfers its SSH endpoint and commits the new account. The existing settings UI continues to use its legacy control commands during this transition.

The private channel exposes process approval counts and bounded activity metadata independently from private material. Activity retains up to 200 completed signing requests from verified peers in the current core. Verified requester command lines are best-effort session data, retrieved separately by activity ID. Account replacement, logout, explicit clear and core exit discard activity. The core and tray persist separate versioned settings.

The production provider calls the public 1Password Go Desktop SDK. One native SDK call at a time may be in progress. The core can cancel its waiter at a deadline, but the SDK's synchronous Windows call can outlive that waiter. Results from expired operations are discarded, and a blocked native call may require restarting the core. Desktop app locking expires vendor permission to make new reads. The core's local cache follows its own policy. New, rotated, archived and deleted items are reconciled on explicit refresh.

The tray creates settings windows on demand. Closing the settings window releases its view and stops status polling. The tray process, private session and approval dispatcher stay available. The settings navigation and expandable cards follow the Windows settings pattern. Tray Quit coordinates process exit.

The tray saves its language, theme and automatic update-check preference in `%LOCALAPPDATA%\opssh\tray-settings.json`. The available BCP 47 language tags are `en` and `zh-Hans`. The default system choice resolves to Simplified Chinese or English using the Windows UI language at startup. Existing explicit choices remain selected. The tray offers system, light and dark themes and defaults to system. Changing the effective language rebuilds Settings and discards unapplied form edits. These preferences are separate from the core configuration. The settings window uses an integrated WinUI title bar with native caption controls. The tray executable declares Per-Monitor V2 DPI awareness.

About offers a manual update check and a startup check toggle, enabled by default. The tray performs at most one automatic check per process launch. It queries the public latest stable GitHub Releases endpoint and compares its numeric version tag to the installed tray assembly version. It bounds the request time and response size. A newer stable release triggers a Windows notification for the startup check and exposes the official release page in About. The tray does not download or install updates.

The Go core wipes application-owned mutable buffers and disposes private key references when they expire. SDK response strings, parser allocations, and cryptographic internals can retain copies outside that control. The app does not write a cleartext private key to disk. This is not protection from paging, dumps or malicious same-account processes. The [desktop validation procedure](../references/1password-desktop-validation.md) records the remaining vendor checks.

## Windows distribution

The tray project Version defines the triplet for the published tray assembly, Go core greeting and Windows packages. The Windows x64 release has a per-user MSI, a Burn EXE containing the same MSI, and a portable ZIP containing the same application payload. The first-party binaries and installers are unsigned.

The MSI owns the app directory under `%LOCALAPPDATA%\Programs\opssh` and the current user's Start menu shortcut. The shared Programs parent and `%LOCALAPPDATA%\opssh` data remain outside the installed application's ownership. The MSI manages maintenance for installations from either entry point. Installer operations refuse to proceed when the tray or core is running so the user can shut down the signing session through Tray Quit. The installer leaves SSH client configuration and process startup settings under user control.
