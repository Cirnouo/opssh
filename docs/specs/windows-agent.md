# Windows agent behavior

The initial Windows x64 implementation consists of the Go agent and the resident C# WinUI 3 tray. The tray starts its exact bundled child and creates a dedicated duplex channel. It hands over only the connected client endpoint and its real process handle. The core verifies the endpoint PIDs against the handle, sends its greeting, and serves the SSH pipe. The control protocol uses length-prefixed UTF-8 JSON v1. Private key material and SSH signing inputs do not cross the tray channel.

The SSH transport is a per-logon byte pipe. It rejects remote clients, reserves the first instance and keeps a fixed pool of 16 overlapped instances. The DACL restricts client access to the logon SID and excludes additional server instance creation. Requests use kernel pipe identity, the last-read logon token, and retained process handles with creation times. The parent chain includes only verified live same-logon instances, with strictly earlier creation times. Missing or unsafe links end traversal. An unidentifiable requester cannot sign. A cached grant matches the exact key and either a verified process instance or the same Windows logon. Windows recorded parentage and connecting-PID identity do not establish an isolation boundary against same-logon code with access to other processes or duplicated handles.

List and Sign follow RFC 9987. The core exposes configured public blobs, Ed25519, and RSA 2048 to 4096 with the SHA-256 or SHA-512 request flag. It returns failure for unsupported operations, including forwarded session-binding, identity mutation and RSA SHA-1. A raw agent signing request provides no verified remote destination. Frame lengths, pending requests and connection concurrency are bounded. Settings copies a PowerShell command that points the current session to the active named pipe. See the [user guide](../user-guide/README.md#select-agent).

The tray uses the signed official 1Password CLI with desktop integration to list accounts and refreshes executable lookup on retry. The picker starts on the first available account in CLI order. It shows the email, with a user name when returned. The chosen account UUID goes to the Go Desktop SDK in its original spelling. The 1Password window authorizes the candidate process. The tray transfers the SSH endpoint after the candidate lists its vaults successfully. Canceling or failing before activation preserves the old account. A successful switch or removal drops the previous scope, public index, cached material, approvals and activity.

The versioned public configuration under `%LOCALAPPDATA%\opssh` stores the account, allowed vaults, cache policies and public index with stable item references and canonical public bytes. New accounts start with discovery disallowed for all vaults. Vault selection is saved immediately. Exclusion retires the affected identities, approvals and private material. Inclusion takes effect on the next manual discovery. Existing item-level rules are retained until their containing vault rule changes. The SDK authorization covers the account.

The index holds up to 64 scoped keys. Discovery scans up to 256 vault overviews and 8,192 item overviews per scoped vault. It filters the active item overviews by SSH category and reads public fields in batches of up to 32 references. An over-limit index stays empty and the workspace explains the limit. The workspace shows scan progress and can cancel the active request. Discovery pauses the old index and retains valid transient state only for entries with identical public material after a complete result. An acknowledged user cancellation restores the previous index only while its account and scope remain current.

Private lookup is delayed until a sign is authorized, or a user explicitly requests preload. Loaded material is checked against the exact requested public key. A signer owns its temporary private material independently of the public catalog. Preload reports safe, localized failure reasons per key. Bulk preload skips loaded keys and keeps successful loads when another key fails.

| State | Owner and lifetime |
| --- | --- |
| Desktop SDK permission | 1Password manages account/process access. The selected account is saved separately from permission. The UI shows the last observed request result and local timestamp, including an expired authorization if reported by the SDK. |
| Loaded private material | The core caches it in memory, fixed 5 minutes by default. Fixed time starts at import; idle time is renewed after successful signing. |
| Use approval | The core keeps it in memory, fixed 10 minutes by default. Fixed time starts at approval; idle time renews after successful signing. Only a successfully published signature installs a reusable grant. |

Each cache supports off, fixed, idle and until-exit modes. Removed cache values migrate through the default fallback for each cache. App approval selects the closest verified live chain member with an eligible top-level window. It covers that instance and subsequent verified descendants. The exact process must remain alive. If no eligible window owner is available, the fallback approval covers only the verified requesting instance. An all-apps approval covers one key in the current Windows logon. It is individually revocable and follows the configured approval expiry policy. Request-only approval applies to one pending signature. The core checks connection, process, key generation and approval before loading and again before signing and publishing. A late result cannot restore invalidated state. Eviction clears only key material. Revocation clears only approvals. Closing or losing the control channel shuts down the core. Reconnection starts with empty caches.

The private channel exposes independent key load state and process approvals. The Activity page retains up to 200 completed signing requests from verified peers in the current core. It shows a verified application and PID, result, key and local timestamp. Best-effort requester command lines are retrieved separately by activity ID and held only for this session. Clearing activity, changing accounts or exiting the core removes the records. Activity filters combine values within a group by union and combine groups by intersection.

The production provider calls the public 1Password Go Desktop SDK. One native SDK call at a time may be in progress. The core can cancel its waiter at a deadline, but the SDK's synchronous Windows call can outlive that waiter. Results from expired operations are discarded, and a blocked native call may require restarting the core. Desktop app locking expires vendor permission to make new reads. The core's local cache follows its own policy. New, rotated, archived and deleted items are reconciled on explicit refresh.

The tray creates the native workspace on demand. Closing the workspace stops UI status polling and leaves the core and approval dispatcher available. The workspace uses an integrated WinUI title bar and left navigation with SSH Keys, Activity, 1Password, Settings and About. Signed-out users can open the account picker, Settings and About. Tray Quit coordinates process exit. The tray presents one signing request at a time through Windows notifications. The notification shows the application, PID and full key fingerprint, with a process icon when available. The action is bound to the pending core session and request until the core deadline. Notification dismissal does not grant access. A disabled or failed notification rejects the request and records the unavailable outcome. Approval-cache-off mode offers request-only approval and denial.

The tray stores its startup behavior, language, theme, update-check and diagnostic preferences separately in versioned tray-settings.json. Settings changes take effect immediately. The tray supports English and Simplified Chinese and resolves the system default from the Windows UI language. Theme can follow the system or be set to light or dark. Changing language rebuilds the workspace. The tray declares Per-Monitor V2 DPI awareness.

Diagnostics are off by default. When enabled, the tray records allowlisted operational phases, outcomes, times and durations. The default level is INFO, with ERROR, WARN and DEBUG also available. Explicit single and bulk preload requests record a DEBUG start and a completion with elapsed time, counts and a safe outcome. The core retains up to 128 completed signing observations in memory and exposes at most 32 at a time through the private control channel. It drops observations when collection is busy and discards stale observations across consent, clear and session changes. Diagnostics omit request contents, signatures, keys, identifiers, command lines, paths and raw error messages.

The tray writes local diagnostics under `%LOCALAPPDATA%\opssh\logs` while the tray is running. It retains up to 1 MiB each in the active log and two rotated files. Settings opens the directory directly in Windows File Explorer, shows the total size of managed logs and clears them after confirmation. Disabling logging leaves existing files available for inspection or clearing.

About offers a manual update check and a startup check toggle, enabled by default. The manual button remains disabled until the in-progress request and result handling complete. The tray performs at most one automatic check per launch. It queries the public latest stable GitHub Releases endpoint with a bounded time and response size and compares the numeric version against the installed assembly. A newer release triggers a Windows notification after an automatic check and exposes the official release page in About.

The Go core wipes application-owned mutable buffers and disposes private key references when they expire. SDK response strings, parser allocations, and cryptographic internals can retain copies outside that control. The app does not write a cleartext private key to disk. This is not protection from paging, dumps or malicious same-account processes. The [desktop validation procedure](../references/1password-desktop-validation.md) records the remaining vendor checks.

## Windows startup and agent selection

Login startup is a current-user registration. Waiting for 1Password subscribes to same-session process start events, with periodic checks when subscription is unavailable. The tray verifies the desktop process and shows a Windows notification when 1Password is ready. Opening the notification brings up the account picker, where the first available account is selected and the current account can be selected if listed. The user confirms the account before the tray requests SDK access. Reauthorizing the current account refreshes its vault list without switching accounts. Tray preferences v3 retain the wait toggle, appearance and update preference from v2 and drop the previous startup action.

A confirmed default-agent change can stop and disable the automatic running inbox OpenSSH agent before reserving its known pipe. The tray refuses other pipe owners and an automatic service that is stopped. Restoring Windows OpenSSH releases the default pipe and sets the installed service to automatic and running. The confirmation dialog stays open to show the service, pipe, persistence and recovery stages as they occur, then shows the outcome. Service steps are skipped when the inbox service is absent. An interrupted service change leaves a recovery record. A pending elevated change remains recorded until the initiating process can establish its outcome. If the process exits during that change, an administrator must reconcile the recorded state before removing the recovery file. Exit releases the pipe and retains the selection for the next startup.

## Windows distribution

The tray project Version defines the triplet for the published tray assembly, Go core greeting and Windows packages. The Windows x64 release has a per-user MSI, a Burn EXE containing the same MSI, and a portable ZIP containing the same application payload. The first-party binaries and installers are unsigned.

The MSI owns the app directory under `%LOCALAPPDATA%\Programs\opssh` and the current user's Start menu shortcut. The shared Programs parent and `%LOCALAPPDATA%\opssh` data remain outside the installed application's ownership. The MSI manages maintenance for installations from either entry point. Installer operations refuse to proceed when the tray or core is running so the user can shut down the signing session through Tray Quit. The installer leaves SSH client configuration and process startup settings under user control.
