# Windows agent behavior

The initial Windows x64 implementation consists of the Go agent and the resident C# WinUI 3 tray. The tray starts its exact bundled child and creates a dedicated duplex channel. It hands over only the connected client endpoint and its real process handle. The core verifies the endpoint PIDs against the handle, sends its greeting, and serves the SSH pipe. The control protocol uses length-prefixed UTF-8 JSON v1. Private key material and SSH signing inputs do not cross the tray channel.

The SSH transport is a per-logon byte pipe. It rejects remote clients, reserves the first instance and keeps a fixed pool of 16 overlapped instances. The DACL restricts client access to the logon SID and excludes additional server instance creation. Requests use kernel pipe identity, the last-read logon token, and retained process handles with creation times. The parent chain includes only verified live same-logon instances, with strictly earlier creation times. Missing or unsafe links end traversal. An unidentifiable requester cannot sign. A cached grant matches the exact key and process instance. Windows recorded parentage and connecting-PID identity do not establish an isolation boundary against same-logon code with access to other processes or duplicated handles.

List and Sign follow RFC 9987. The core exposes configured public blobs, Ed25519, and RSA 2048 to 4096 with the SHA-256 or SHA-512 request flag. It returns failure for unsupported operations, including forwarded session-binding, identity mutation and RSA SHA-1. A raw agent signing request provides no verified remote destination. Frame lengths, pending requests and connection concurrency are bounded. The SSH client selects the opt-in pipe in its own environment. See the README for selection and rollback.

The public configuration is stored under `%LOCALAPPDATA%\opssh`. It contains the selected account, item references, policies, names and canonical public key bytes. Refresh disables the old identity before reading the new public field. The selected item remains visible if the public lookup fails. Private lookup is delayed until a sign is authorized, or a user requests preload. Loaded material is checked against the exact requested public key. A signer owns its temporary private material independently of the public catalog.

| State | Owner and lifetime |
| --- | --- |
| Desktop SDK permission | 1Password manages account/process access. The UI shows observed request state, including recent success, failure and timeout. |
| Loaded private material | The core caches it in memory, fixed 5 minutes by default. Fixed time starts at import; idle time is renewed after successful signing. |
| Use approval | The core keeps it in memory, fixed 10 minutes by default. Fixed time starts at approval; idle time renews after successful signing. Only a successfully published signature installs a reusable grant. |

Each cache supports off, fixed, idle and until-lock modes. Host approval includes the host itself and subsequent verified descendants. The exact host must remain alive. Direct mode covers the requesting instance. Once applies to one pending request. The core checks connection, process, key generation and approval before loading and again before signing and publishing. A late result cannot restore invalidated state. Eviction clears only key material. Revocation clears only approvals. Lock clears both and keeps the public index available. Closing or losing the control channel shuts down the core. Reconnection starts a new core and an empty approval state. Account switching restarts the core and resets the selected index.

The production provider calls the public 1Password Go Desktop SDK. One native SDK call at a time may be in progress. The core can cancel its waiter at a deadline, but the SDK's synchronous Windows call can outlive that waiter. Results from expired operations are discarded, and a blocked native call may require restarting the core. Desktop app locking expires vendor permission to make new reads. The core's local cache follows its own policy. Rotation or deletion is reconciled on explicit refresh.

The Go core wipes application-owned mutable buffers and disposes private key references when they expire. SDK response strings, parser allocations, and cryptographic internals can retain copies outside that control. The app does not write a cleartext private key to disk. This is not protection from paging, dumps or malicious same-account processes. The [desktop validation procedure](../references/1password-desktop-validation.md) records the remaining vendor checks.
