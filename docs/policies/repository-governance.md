# Repository governance

## Branch and pull request lifecycle

1. Inspect the current checkout and base the change on current `main`. Use one focused lowercase topic branch with a kebab-case topic, such as `docs/contributor-workflow` or `fix/approval-timeout`. Omit the `codex/` prefix. Use one isolated managed worktree and one PR for the change.
2. When working in Codex, use its managed worktree action when available. Confirm the chat is bound to the intended checkout and run `git rev-parse --show-toplevel` and `git branch --show-current` in the worktree before editing, committing or pushing. If Codex still reports the previous checkout after worktree creation, reselect or rebind the managed worktree and confirm the association in Codex.
3. Stage related changes together and use independently reviewable, atomic Conventional Commits. Review the staged diff and run the [local gate](verification.md#local-commit-gate) in that worktree. Preserve the configured commit signer. When signing a tree validated on another machine, verify the signed commit has the same gated tree and rerun the required checks on the final signed SHA. A `gpt-6-luna` high subagent runs and follows the final local checks before push and reports the outcomes. Use `gpt-6.1-sol` ultra for decision and review subagents. Do not use `gpt-6-astra`.
4. Open the focused PR into `main` with a Conventional Commit title and the [PR template](../../.github/PULL_REQUEST_TEMPLATE.md). Attach the new PR to the current Codex chat immediately and confirm the chat shows that PR. Link issues the change resolves with closing keywords. Describe the final behavior, compatibility or security implications and the actual verification. Keep the PR number suffix out of its title.
5. Have a `gpt-6-luna` medium subagent follow CI for the latest PR revision. Identify the PR head SHA and the test merge SHA actually checked out by the pull-request workflow. Recheck after a head or base update. For signed topic commits, confirm GitHub's verification on the exact PR commits. Merge only after the latest applicable checks pass and the review is resolved.
6. Squash with `<PR title> (#<PR number>)` as the subject. Include the suffix if supplying an explicit CLI subject and verify the merged subject and PR association. Have a `gpt-6-luna` medium subagent follow CI for that exact new `main` SHA. Once it passes, fetch and fast-forward local `main` in its own checkout. Preserve any unrelated local work.
7. After successful main CI, retain the managed topic worktree while it serves as the current or pending chat checkout. Archive it through Codex once eligible, then confirm the chat still shows the PR. If archiving clears the attachment, reattach the same PR through Codex and verify it again. If Codex defers archiving because the worktree is bound, retry through Codex only after that association ends.

## Main rules and rollout

The target ruleset for an authorized rollout to `main` requires PRs, squash-only merging, linear history and successful checks with strict up-to-date enforcement. It prevents branch deletion and non-fast-forward updates, has zero required approvals and grants no bypass, including to administrators. Keep review evidence in the contribution workflow.

The [Windows validation workflow](../../.github/workflows/windows.yml) runs the offline Windows build and tests, checks the Release folder, and uploads that folder on PR and `main` events. Before making a check required, run it successfully on both events and record the exact emitted check context and GitHub App integration ID. Use the same rollout for added commit, dependency or code-scanning checks. Record skipped checks, missing scanner results and unavailable audit services separately from success. Review initial scanner results before enforcing a scanning rule.

Remote rules and repository settings require authorization before applying changes. Inspect repository settings, configured rulesets, effective `main` rules and legacy branch protection. Save recoverable pre-change responses privately, omit server-assigned fields from update payloads and keep unrelated settings intact. A missing legacy protection record can coexist with an effective ruleset. Apply only authorized changes, then read back the settings and effective rules and verify the required-context mapping. Keep the rule in force while resolving failed checks.

## Releases

Keep PR and `main` validation separate from publication. Obtain authorization for tagging and publishing even when release automation is configured. Follow the [stable release policy](releases.md) for the verified source, the changelog, the MSI and the publication procedure.
